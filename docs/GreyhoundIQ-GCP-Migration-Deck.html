A · Top risk found

The one thing we fix before anything else

The single biggest threat to your data isn't traffic — it's an existing pipeline that can legally run a full wipe against production.

! prisma/seed.ts is a wipe-and-reseed

It opens with deleteMany() across ~25 tables — users, profiles, listings, messages, conversations, forum posts — then inserts sample data.

And the supabase-migrate workflow lets an operator pick environment: production with seed: true. One dropdown from total data loss.

Footguns nearby: db:reset (migrate reset --force) and db:push.

🛡 How this plan closes it

  • Seed refuses to run when the target looks like production (env + DB-host guard)
  • Remove the production option from any seed workflow entirely
  • CI grep-gate blocks reset, db push, TRUNCATE, and DELETE without WHERE
  • Production uses migrate deploy only — forward-only, reviewed, approved
  • Point-in-time recovery + verified restore drill as the backstop
Non-negotiable
No CI/CD job, deploy script, or preview workflow may wipe, overwrite, reset, or reseed production data. Data safety outranks every other goal in this plan.

E · CI/CD design

Build once, promote the same image, gate production

GitHub Actions with Workload Identity Federation (keyless) into GCP. The exact artifact tested on staging is what ships to prod.

PR

Checks

install · typecheck · lint · unit · build · npm audit · destructive-command gate

MAIN

Staging

build & push image → deploy staging → migrate deploy (staging DB) → smoke tests

GATE

Manual approval

release owner approves. Migrations approved separately.

PROD

Promote

deploy same digest → smoke tests → auto-rollback revision on health fail

🔑 Keyless

WIF federation — no long-lived service-account keys in GitHub. Prod secrets bound to the prod environment only.

🧱 Guarded

CI fails on reset, db push, TRUNCATE, or DELETE-without-WHERE in any migration or script diff.

↩ Reversible

Rollback = route traffic to the previous Cloud Run revision. Seconds, and the database is never touched.

F · Database protection plan

The rules that keep production data alive

🧬 Migrations

Forward-only, expand-and-contract. No DROP/TRUNCATE/un-scoped DELETE without explicit human approval. prisma migrate deploy only in CI/prod — never reset or db push.

💾 Backups & restore

Supabase PITR + daily snapshots. Quarterly restore drill to a scratch project to prove recovery, with a documented RTO/RPO.

🌱 Seed data

Seed is dev/staging only, guarded to abort if the DB host looks like prod. The production seed path is deleted.

🔐 Keys & access

Service-role key server-only in Secret Manager, never shipped to the browser. RLS on client-reachable tables/buckets. Separate Supabase projects for staging vs prod.

Break-glass
Emergency prod DB access is a named, logged, time-boxed procedure — not a default credential sitting in anyone's .env.

E/G · Secrets & identity

Keyless deploys, least-privilege everywhere

🪪 Workload Identity Federation

GitHub Actions authenticates to GCP via short-lived federated tokens. No downloadable service-account keys to leak or rotate.

🗝 Secret Manager

All secrets — DB URLs, WorkOS, Lago, Topaz, internal secrets — live here. Staging and prod secrets are separate and env-scoped.

👤 Per-service accounts

Distinct least-privilege SAs for web, jobs, scheduler, and deploy. No shared write identity between staging and prod.

Public vs private env

public NEXT_PUBLIC_SUPABASE_*, NEXT_PUBLIC_WORKOS_REDIRECT_URI   ·   server-only service-role key, WORKOS_API_KEY, Lago keys, INTERNAL_API_SECRET, DB URLs.

Log hygiene

Secrets never printed in CI logs; production DB URL never appears in .env.example or public logs; compromised secrets rotated on a documented runbook.
