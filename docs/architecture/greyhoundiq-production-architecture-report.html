01 · Executive verdict · corrected 16 July mandate

One Australian web MVP. One fail-closed release authority. Native apps later.

GreyhoundIQ’s selected production shape is a Google defensive edge feeding Sydney and Melbourne Cloud Run cells, a contract-driven API boundary, a stateless modular monolith plus isolated workers, Australian object/event storage, and a single-writer PostgreSQL/Prisma data plane with rehearsed Melbourne recovery. Application realtime uses regional Cloud Run WebSocket gateways, an AlloyDB transactional outbox, AU-restricted Pub/Sub, separate per-region application Memorystore and cursor replay. Existing one-to-one voice/video uses independent self-hosted Sydney and Melbourne LiveKit cells with room-home assignment, per-cell HA Redis, tested N+1 SFU capacity, TLS signalling and explicit UDP/ICE/TURN paths; active calls do not migrate across a regional failure. There is no production user/customer dataset to migrate: AlloyDB is bootstrapped empty with forward-only Prisma migrations, synthetic staging fixtures and approved racing-provider rehydration. Native iOS/iPadOS and Android store apps remain separate post-MVP codebases and do not block web launch. Design Lab is the authenticated simulation, training, observability and Founder control layer—not a shortcut around protected production approval.

Facts · assumptions · missing inputs

Honest inputs before capacity

Repository evidence, the new-account read-only preflight and target design are labelled separately. Provisional workload values remain launch blockers until measured or approved.

Most important missing inputs: what “50,000 users” means; route mix and session length; real concurrency; CPU and memory per route; transaction duration and DB limits; response/upload sizes; cacheability; realtime connections/messages; feed/provider SLAs; data volume/growth/retention; legal residency; availability/RTO/RPO; cost ceiling; and trained on-call coverage.

Known code and new-account facts

  • Next.js/TypeScript web application; native iOS/iPadOS and Android store apps are separate post-MVP repositories and do not block web launch.
  • No production users or production customer dataset exists to copy; production AlloyDB starts empty.
  • Prisma 6.19/PostgreSQL; request/system work uses interactive DB transactions and database normalisation gates remain open.
  • The active GreyhoundIQ identity owns one billing-enabled free-trial project candidate, but no target Cloud Run, AlloyDB, load-balancer, storage, queue, monitoring or LiveKit resource has been provisioned or verified.
  • The repository's legacy workflow declares public single-region Cloud Run with default URLs; it is source evidence of an unsafe obsolete path, not live inventory for the new account.
  • The target API gateway, AlloyDB, application Memorystore, Pub/Sub, Cloud Storage and independent regional LiveKit cells are not deployed; no current backend exists from which CDN status can be inferred.
  • Thirteen racing-data pipelines are code-inventoried, but authoritative per-feed runtime health, ownership, licence, SLA, alert and runbook evidence is absent.
  • OpenAPI 3.0.3 covers 85 paths/106 operations; zero-error static Spectral evidence does not replace deployed negative tests.

Residency boundary

“Australia only” means Australian application compute and selected persistent application data. Google’s CDN/DNS/Monitoring and Secret Manager service semantics are global. Public CDN objects can be cached globally. WorkOS, Stripe and other authorised overseas providers require explicit cross-border and availability review; the self-hosted LiveKit media plane remains on Australian compute. Legal/DPA approval remains a launch gate for affected MVP journeys.

The database equation closes before the autoscaler

09
CDN, WAF, bot and DDoS

Reject hostile work at the cheapest layer

The origin is never sized to process arbitrary attack traffic. Edge controls absorb volumetric traffic, challenge or deny abusive HTTP traffic, and preserve a bounded admission budget for authenticated critical journeys.

DNS and domain

  • Cloud DNS anycast; registrar lock and phishing-resistant MFA
  • DNSSEC with registrar DS and rehearsed disable order
  • 300 s cutover TTL; normal 3600 s where safe
  • Certificate alerts at 30/14/7/1 days
  • Two-person reviewed zone/config rollback

CDN contract

  • One-year immutable hashed assets
  • Explicit public-media/public-read allowlist
  • Authenticated, tenant, admin, billing, messages and writes: private, no-store
  • Origin headers own TTL; no mixed FORCE_CACHE_ALL
  • Signed private access, purge/version and poisoning tests

Origin shield

  • Cloud Run ingress: internal and Cloud Load Balancing
  • Disable default URL on public web/API/realtime; retain only IAM-protected internal endpoints required by Google callers
  • No alternate A/CNAME or public object-store origin
  • Exact provider webhook paths only; signature and replay checks always
  • External direct-origin probe must fail
Cloud CDN is global. Public cacheable objects can be stored outside Australia and no city cache is guaranteed. Therefore private, authenticated, tenant-specific and legally restricted data never enters the shared CDN. Sydney/Melbourne storage is the authoritative object origin; legal approval owns the public-cache exception.

Cost-exhaustion ceiling

Cloud Run max instances are per revision and can be exceeded temporarily; they are not a hard financial ceiling. Protect cost with edge rejection, aggregate app admission, per-route/user/tenant/resource complexity quotas, separate worker caps, bounded queue depth, upload/report/AI budgets, logging sampling, 50/75/90/100% spend-velocity alerts and pre-tested optional-feature shutdown at 90%.

10
API gateway and load balancing

Three layers, three non-overlapping owners

GreyhoundIQ needs CDN + global external Application Load Balancer + ESPv2. It does not need managed API Gateway plus ESPv2, per-service internal load balancers or speculative service proxies.

Global edge / ALB

TLS, URL map and regional routing

Terminates TLS, preserves the trusted client-address chain, applies Armor/CDN, maps web/assets/API/webhook/admin paths and routes each request to the closest available functionally equivalent Sydney/Melbourne serverless NEG. Health-based failover requires Cloud Run service health/readiness, at least one minimum instance in each region, regional synthetics and a controlled failover test.

ESPv2 / Endpoints

Coarse API policy

Reject undeclared operations, validate supported token/API-key identity, enforce operation quotas and body/header/deadline budgets, version the API and emit per-operation telemetry. Generate Google extensions from the canonical OAS3 document; do not fork the contract.

Application + RLS

Queue and worker architecture

Durable intent before asynchronous convenience

Critical job intent is committed in the same PostgreSQL transaction as the business change, then relayed through Pub/Sub regional endpoints under a Sydney/Melbourne message-storage allowlist. That policy controls where Pub/Sub may persist messages; it does not copy every message to both regions. A topology ADR must select shared versus per-region topics/subscriptions and prove regional publish, backlog and replay behaviour. Sydney-only Cloud Tasks remains limited to reconstructable scheduling/throttling.

JobProducer / arrival modelDelay SLORetry/idempotency/orderConcurrency/downstream protectionDLQ/replay

Queue invariants

  • At-least-once is assumed; every consumer deduplicates
  • Schema version, idempotency key and causal entity ID required
  • Retry deadline and max attempts per job class
  • Oldest age, arrival/completion, retries and DLQ alert
  • Unknown schema/poison message quarantines without blocking partition
  • Manual replay is scoped, audited and dry-run reviewed

Regional topology gate

Use regional endpoints. The ADR must name topic/subscription ownership, publish failover, persistence policy, duplicate semantics, ordering limits, backlog recovery and regional-loss user mode. Until that drill passes, the queue is not claimed as dual-region durable.

Worker overload rule

Worker concurrency = arrival_rate × average_duration ÷ 0.70, but the result is capped by the destination’s DB/API budget. Scenario B 10× produces an illustrative 1,125 jobs/s and ~804 worker concurrency at the placeholder mix—therefore optional jobs must backlog or disable rather than blindly create 804 workers.

Backup and disaster recovery

A successful backup job is not a successful restore

Recovery is measured from incident declaration to validated user journeys and data integrity—not merely to a database endpoint becoming reachable. Emergency AlloyDB cross-region promotion is asynchronous and non-zero-RPO; planned zero-loss switchover is credible only while both regions are healthy and caught up.

Backup contract

  • Continuous PITR sufficient for target RPO
  • Daily retained copies and approved long-term schedule
  • Encrypted, isolated production access and cross-project AU recovery copy
  • Deletion protection/immutability and audited restore role
  • Backup age/completion and restore-test alerts

Restore cadence

  • Monthly representative row/table/PITR restore
  • Quarterly abrupt regional promotion, reconciliation and failback
  • Separate healthy planned-switchover exercise
  • Annual account-compromise reconstruction
  • Validate schema, RLS, counts, invariants, authz and app smoke
  • Record actual RTO/RPO and remediation

Current verdict

Production topology, backup retention, immutable isolation, restore time, point-in-time loss, writer fencing, Sydney failover and Melbourne promotion are unverified. Every recovery target is conditional, and zero-RPO is not claimed for emergency regional loss.
