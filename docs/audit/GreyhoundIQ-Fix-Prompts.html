Phase 1 — Critical security / RLS
CRITICALP1-AVerify RLS role + enforce it at the DB layer
Verify and harden RLS enforcement for GreyhoundIQ's Prisma-to-Postgres path. Do NOT change app logic yet.
1. From inside the VPC (or via a one-off admin task using DB_ADMIN_URL), confirm for the runtime role
   `greyhoundiq_app`: `rolbypassrls=false`, `rolsuper=false`, and that it is NOT the owner of the public
   tables (owner should be greyhoundiq_migrator/postgres). Record results.
2. Add a forward-only migration that runs `ALTER TABLE "<t>" FORCE ROW LEVEL SECURITY;` for every table
   that already has RLS enabled (the ~65 in 20260706223000). This closes the owner-bypass gap and makes
   RLS authoritative regardless of connecting role.
3. Extend scripts/check-rls-policies.ts to assert (a) rolbypassrls=false for the runtime role and
   (b) relforcerowsecurity=true for every RLS table, so CI fails if this regresses.
Do NOT touch policy predicates. Test: npm run check:rls-policies, typecheck, lint, build.
Rollback: the migration only sets FORCE RLS; a follow-up migration can NO FORCE if it breaks a path.
CRITICALP1-BMake DB request/system context mandatory on every Prisma access
Audit every Prisma call site in src/ for missing RLS context. Any request-scoped data access must go
through withDbRequestContext(current, ...); any cron/system/maintenance/webhook path must go through
withDbSystemContext(...). Specifically fix src/lib/listing-service.ts runListingMaintenance (currently
raw prisma.$transaction with no context - under FORCE RLS it will no-op/deny) to use withDbSystemContext,
and sweep for other direct prisma.* usages in services/routes (memory, reports, maintenance jobs). Prefer
one shared wrapper over per-callsite fixes. Add a lint/check script (extend an existing check:* script)
that greps for direct `prisma.` usage outside db.ts/db-context.ts and flags un-wrapped access.
Test: run each affected cron endpoint locally against a FORCE-RLS DB; npm run check:community-flow,
check:comms-security, typecheck, lint, build. Rollback: revert wrappers per file.

system/mod paths. Replace the fully-open RateLimit policy with system-context-only writes (the limiter
runs under system context). Verify the app's audit-write and rate-limit code paths set the right context
first (update them if they don't). Test: check:rls-policies, check:comms-security, unit tests, build.
Rollback: single follow-up migration restoring prior policies.
HIGHP1-DAdd RLS to the 28 unprotected tables (defense-in-depth)
Add RLS + policies to the 28 tables currently without it, prioritizing sensitive ones first: Report,
DeletionJob, ExportArtifact, Organization, Membership, MemoryEntry, TrustSafetyFlag, OrganizationInvitation,
SupportTicket, SupportMessage, then the rest. Mirror the existing ownership/moderator/system pattern from

the existing migration. Verify each table's read/write app paths already set context (they must, post P1-B).
Do this in small batches with a check:rls-policies assertion per table. Test after each batch. Rollback:
per-table drop-policy migration.
